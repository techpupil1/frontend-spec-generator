# 八大模块

这八个模块必须逐个确认，不要一次性把所有问题丢给用户。

## 1. 视觉风格

需要确认：

- 整体气质和产品感受
- 色彩方向
- 字体风格
- 信息密度、间距、圆角、层次感
- 是否需要暗色模式

推荐提问方式：

- 先给出你对产品气质的简短理解。
- 用用户体验感受对比选项，例如“干净克制”对比“信息密度高、功能感强”。

## 2. 技术方案

需要确认：

- 框架或平台技术栈
- 语言层级
- 构建工具
- 包管理器
- 路由方式
- 数据获取与 API 交互模型

推荐提问方式：

- 把取舍翻译成交付速度、招聘与维护成本、避免 bug 的能力，以及后续扩展灵活性。

## 3. UI 组件库

需要确认：

- 组件库策略：原语型、半成品型，还是开箱即用型
- 必要的组件类别
- 图表、编辑器、上传等特殊组件需求

推荐提问方式：

- 讲清用户保留多少视觉自由度，以及能换来多少实现速度。

## 4. 目录结构

需要确认：

- 按功能组织还是按技术层组织
- 具体目录树
- 命名规范
- 导入边界

推荐提问方式：

- 讲清团队是在优化“改一个功能集中在一个地方”，还是“技术职责拆分更清楚”。

## 5. 模块边界

需要确认：

- 页面是否可以直接调用 API
- 状态归属和通信方式
- 公共逻辑提取边界
- 模块依赖方向

推荐提问方式：

- 讲清每种选择对调试清晰度、耦合程度和长期可预测性的影响。

## 6. 复用规则

需要确认：

- 何时提取共享组件
- 业务组件与通用组件的划分标准
- 工具函数放置规则
- 常量、枚举和共享类型规则

推荐提问方式：

- 同时避免过早抽象和无节制重复。

## 7. 样式系统

需要确认：

- 样式方案
- Token 或颜色系统
- 暗色模式实现方式
- 响应式断点
- 动效与过渡规则

推荐提问方式：

- 除了编写速度，还要讲清维护成本和主题扩展弹性。

## 8. 实施计划

需要确认：

- 阶段划分
- 优先级顺序
- 任务依赖关系
- 哪些属于第一阶段必须做，哪些适合后续优化

推荐提问方式：

- 产出一份会随着交付推进而持续更新的活清单。

## 模块推进节奏

每个模块都按这个节奏推进：

1. 先总结你当前的建议。
2. 用结果导向语言解释选项。
3. 只问这个模块必须确认的决策。
4. 在进入下一模块前复述已确认结果。
