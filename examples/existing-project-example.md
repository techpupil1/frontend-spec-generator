# 示例：已有项目规范输出

## 输入摘要

仓库已经使用 `React + Vite + Tailwind`，有基础页面和接口联调能力，但目录结构按时间自然生长，团队目前缺少明确的模块边界、复用规则和样式约束。

## 示例规范

# CRM 管理后台前端规范

## 1. 视觉风格

### 已确认方向

延续当前偏业务化、信息密度中高的后台风格，不做品牌重设计，只做一致性收口。

### 设计规则

- 强调表格、筛选、详情面板等高频业务视图的清晰度
- 色彩以中性灰和蓝色主强调为主，避免页面色彩过载
- 表单控件、列表间距、标题层级统一

### 备注

本次规范目标是统一体验，不是全面改版。

## 2. 技术方案

### 已确认方向

保留现有 `React + TypeScript + Vite + Tailwind` 技术栈，不做迁移。

### 决策理由

- 当前团队已经基于这套栈完成部分业务，迁移收益不足以覆盖成本
- 主要问题不在栈，而在组织方式和约束缺失
- 用规范约束先解决扩展性问题，比更换技术更直接

### 约束条件

- 近期不引入重型状态管理框架
- 保留当前构建链路和发布方式

## 3. UI 组件库

### 已确认方向

继续使用现有基础组件，并逐步收敛成统一业务组件层。

### 组件范围

- 表格、分页、筛选栏、表单项、弹窗、抽屉、消息提示
- 统计卡片、详情描述块、状态标签

### 特殊组件

- 日期范围筛选组件
- 权限敏感的操作按钮封装

## 4. 目录结构

### 已确认方向

从当前按页面散落的方式，收敛到按业务功能组织。

### 建议目录树

```text
src/
  app/
  shared/
  features/
    customer/
    lead/
    contract/
    dashboard/
  pages/
  widgets/
```

### 命名与导入规则

- `pages/` 只保留页面入口和路由装配
- 业务逻辑、接口、类型、局部组件尽量跟随 `features/`
- `shared/` 仅承载真正跨业务复用内容

## 5. 模块边界

### 已确认方向

页面层不直接处理复杂业务逻辑，业务流程和数据组装下沉到功能模块。

### 状态与通信规则

- 页面负责路由和区域拼装
- 功能模块负责接口调用、数据映射、表单校验
- 全局状态只保留登录态、权限信息、布局配置等少量共享内容

### 依赖规则

- 禁止页面之间互相引用内部实现
- 禁止一个功能模块直接读写另一个功能模块的私有状态
- 共享逻辑必须通过明确公共接口暴露

## 6. 复用规则

### 已确认方向

优先清理“名字一样但实现不同”和“实现一样但重复拷贝”这两类问题。

### 提取阈值

- 同类业务组件出现 3 次以上且交互一致时提取
- 带强业务语义的组件保留在业务模块中
- 纯展示和纯交互组件才进入共享层

### 共享代码规则

- API 请求封装按业务域组织
- 工具函数必须标明业务归属或明确无业务语义
- 类型定义避免无边界集中堆积

## 7. 样式系统

### 已确认方向

保留 Tailwind，但补充统一的语义层和组件样式约束。

### Token 与主题规则

- 建立状态色、文字色、边框色、背景色语义映射
- 避免组件内直接拼接大量一次性色值
- 表格、表单、筛选栏、按钮尺寸统一分级

### 响应式与动效规则

- 后台以桌面优先，移动端只保证基础可访问
- 动效仅用于弹窗、抽屉、筛选区切换等必要反馈

## 8. 实施计划

### 阶段 1

- [ ] 梳理现有页面和业务域，建立 `features` 分层
- [ ] 收敛公共组件和共享样式 Token
- [ ] 统一表格、表单、筛选栏用法

### 阶段 2

- [ ] 整理接口调用边界
- [ ] 将复杂业务逻辑从页面层下沉到功能模块
- [ ] 清理重复组件和重复类型定义

### 阶段 3

- [ ] 补齐模块依赖约束
- [ ] 逐页迁移历史页面
- [ ] 建立新页面开发准入清单

### 依赖关系

目录重组要先于批量页面迁移；共享组件收敛要先于视觉一致性清理。

### 优先级说明

先解决结构和边界问题，再处理视觉细节和局部体验优化。
